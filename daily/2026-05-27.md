## 笔记摘要

### Agent Identity

核心：Agent 身份把 Agent 从临时会话变成**可发现、可验证、可追责的经济参与者**。

**身份构成要素：**
- Agent Profile — 公开说明文件（是谁、能做什么、怎么联系）
- Capability — 能力声明：能完成什么任务、需要哪些输入和权限
- Service Endpoint — 外部系统调用 Agent 的入口
- Registry — 登记、发现和更新 Agent 身份的目录
- DID + Verifiable Credential — 去中心化身份和可验证声明模型
- A2A — Agent 与 Agent 之间如何发现、通信、协商、交换结果
- Ownership — 谁能更新 profile、收款地址、endpoint 和权限

**身份是信任的第一层，但不等于可信。** 先知道对象是谁，再看它做过什么、谁评价过它、是否有 stake、是否有验证证明。

Agent Identity 是以下三者的前置条件：
1. Agent Trust（信任）— 确认身份后才能评估可信度
2. Machine Payment（机器支付）— 付款前必须知道付给谁
3. Agentic Commerce（Agent 经济）— 交易双方需要可验证的身份凭证

### Agent Trust & Reputation

**可信度的来源：可验证行为 → 不是自我声明。**

信任系统的组成部分：
- Reputation — Agent 历史表现形成的信号集合
- Review — 用户/客户/其他 Agent 对任务结果的反馈
- Attestation — 某主体对 Agent、任务或结果的可验证声明
- Stake — Agent 或运营方押上的经济保证
- Slashing — Agent 违约/作弊/输出虚假结果时罚没抵押
- Validation — 对 Agent 能力或任务结果的验证流程
- ERC-8004 — Agent 身份、声誉和验证 registry 的标准草案

**Stake 设计需明确：** 抵押什么资产、锁多久、什么条件下释放/罚没、罚没给谁。

**定位：** Agent Trust & Reputation 连接 Agent Identity、Settlement & Escrow 和 Machine Payment。没有信任层，Agent 之间无法安全委托；没有声誉和验证，用户难以判断哪个 Agent 值得付款。

**不要过度相信声誉分数。** 真正可靠的系统应该同时看：身份、任务历史、评价者、证明、stake、争议记录和上下文适配度。

### AI Oracle

**核心：把模型判断变成可记录、可验证、可挑战的链上输入。**

不是让模型替合约做判断，而是让 AI 输出有来源、边界和争议机制。

关键概念：
- AI Output — 模型给出的结果（文本、标签、分数、JSON、决策建议）
- Data Feed — 持续提供模型处理后的数据流
- Model Result — 需包含模型版本、prompt/任务模板、输入引用、输出字段
- Attestation — 证明某个主体或执行环境对 AI 输出作出了声明
- Proof of Inference — 试图证明输出确实来自某模型和输入（明输入输出，ZK 证明关键后处理）
- Dispute / Challenge — 对 AI Oracle 输出提出异议的机制

**风险面：** 模型错误、输入污染、prompt injection、数据偏差、执行环境被篡改、输出不可复核、经济攻击。

**争议窗口设计：** 小额任务短窗口，较高价值任务长窗口，高争议任务进入人工或多方 evaluator。
