## 笔记摘要

### Agent Wallet

核心矛盾：Agent 的自主权 vs 用户的控制权。

Session Key 不是传统意义上的委托（无限额度），而是时间绑定的能力令牌——允许 Agent 在一段时间内、在指定范围内自动执行某些动作。Agent 负责生成候选动作，Guard 必须负责拒绝越界动作。所有自动化权限都应有用户可见的关闭入口。

Guard 分两层：
- 链上 Guard — 合约里的规则引擎，检查 calldata/value/target
- 链下 Guard — 策略检查（单笔限额、日累计限额）
前者防恶意合约，后者防模型幻觉。

AI ↔ Wallet 的接口层是 Action Schema：模型输出结构化动作 `{action: "transfer", params: {to: "0x...", amount: "0.01"}}`，Wallet 层解析、验证、签名、提交。直接输出自然语言让钱包猜就是不靠谱的信号。

这个架构与 ERC-7579 / Modular Smart Accounts 天然契合：Smart Account 是身份层，Modules 是权限层，Session Key 可以挂载为 Module。

### Machine Payment

核心：把"付款意图"和"实际结算"拆开，让每一步都有凭证。

传统支付（人发起→签名→转账）是单点不可逆的。机器支付需要变成：意图 → Policy Check → Quote Lock → Escrow Hold → 服务交付 → 结算释放

Quote 不只是报价，而是服务方的绑定承诺——一旦 Agent 签名确认，服务方就不能改价。

Policy 层是整个架构里唯一跟 AI 模型无关的组件——可以用确定性代码写，做静态分析、额度稽核，可以被审计被测试。

信任等级分层：
- 完全信任 → 直接结算（自有服务）
- 半信任 → 延迟结算 + 争议期（长期协作）
- 零信任 → Escrow + 条件释放（匿名 Agent 市场）
- 微信任 → 按次结算 + 收据（小额查询）

### Settlement & Escrow

核心：结算不是"把钱打过去"，而是把任务、交付、验收和付款绑定成可验证流程。

ERC-8183 vs ERC-8004 的定位：
- ERC-8004（身份层）：Agent 身份、声誉、验证——"这个 Agent 是谁？可信吗？"
- ERC-8183（任务层）：Agent 任务、支付、托管、交付——"要做什么？怎么付？怎么验收？"
两者互补，一个完整 agent commerce 系统通常都需要。

Escrow 解决了"付了钱但服务没交付"的问题——资金被锁定，直到双方确认条件满足才释放。对于 AI Agent 自动化交互，超时自动回滚是最后的保障线。

### 三章的联系

这三章构成递进的权限粒度：
1. Agent Wallet — 谁能动我的钱（身份 + 权限），用 Session Key 限制
2. Machine Payment — 能付多少钱、给谁付（意图 + 结算），用 Policy 限制
3. Settlement & Escrow — 付了能拿到东西吗（交付 + 验收），用 Escrow 保证

如果把 Agent commerce 比作人去中心化的 Fiverr：8004 是 Agent 的名片和声誉，8183 是每次任务的工单和付款条款。
