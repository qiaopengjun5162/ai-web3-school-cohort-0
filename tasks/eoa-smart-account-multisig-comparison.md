# EOA、智能账户、多签的权限差异

> 基于 AI × Web3 School Handbook 学习总结

---

## 对比总览

| 维度 | EOA（外部账户） | Smart Account（智能账户） | Multisig（多签） |
|------|----------------|-------------------------|-----------------|
| **控制权** | 单个私钥全权控制 | 合约逻辑定义权限规则 | M-of-N 个签名者共同控制 |
| **发起交易** | 私钥签名即可 | 可通过 EOA 或 Session Key 发起 | 需要 N 个签名者中的 M 个批准 |
| **多人确认** | ❌ 不支持 | ✅ 可通过策略配置实现 | ✅ 核心功能（M-of-N） |
| **恢复/限额/自动化** | ❌ 无恢复机制，无额度限制 | ✅ 支持限额、白名单、时间锁、Session Key、可编程恢复 | ✅ 可配合时间锁、额度提案 |
| **典型场景** | 个人日常使用、初期 DApp 交互 | AI Agent 钱包、GameFi 会话、订阅支付、企业资金管理 | DAO 金库、大额资金管理、团队协作 |
| **主要风险** | 私钥丢失=账户丢失；无权限分层；签名即授权无法撤回 | 合约漏洞风险（Reentrancy、逻辑 Bug）；Gas 成本较高；需理解政策配置 | 治理攻击（少数签名者合谋）；提案审批延迟；部署复杂度高 |

---

## 逐类深入分析

### 1. EOA（Externally Owned Account）

**如何工作：** 私钥签名交易 → 节点验证签名 → 交易写入链

**关键特征：**
- 私钥 = 全部权限，没有分层、没有限制
- 没有"只读"或"限额"模式——签名就是完整授权
- 没有恢复机制——私钥丢失 = 账户永久丢失

**适合：** 个人测试、小额日常使用、对安全要求不高的场景

**不适合：** Agent 自动化、团队协作、大额资产管理

**必须在人工确认的操作：** 所有操作——因为签名即最终授权

---

### 2. Smart Account（智能账户）

**如何工作：** 合约逻辑定义授权规则 → EOA 或 Session Key 发起调用 → 合约检查策略 → 执行或拒绝

**关键特征 (与 Agent 场景最相关)：**
- **Session Key：** Agent 持有临时、限额度、限操作的子密钥，Owner 保留完全控制权
- **Policy 引擎：** 可以配置白名单合约、白名单方法、单笔限额、日限额、速率限制
- **可编程恢复：** 可以通过社交恢复、时间锁或预设继承人找回权限
- **撤销灵活：** Owner 随时可以撤销全部或部分 Agent 权限

**适合：** AI Agent 钱包、自动支付、GameFi 会话、订阅服务、企业资金管理

**不适合：** 需要固定 M-of-N 组织的场景（这时 Multisig 更合适）

**必须在人工确认的操作：**
- 高风险操作（大额转账、修改策略、所有者变更）
- 超出 policy 限额的操作
- 首次与新合约交互（取决于 policy 配置）
- 撤销 Agent 权限

**Agent 场景的最佳实践：**
```
Agent 持有 Session Key（限1 ETH/天，白名单合约） → 自动执行小额操作
Owner 持有恢复密钥 → 人工确认高风险操作 + 可随时撤销 Agent
```

---

### 3. Multisig（多签账户）

**如何工作：** 需要 M-of-N 个签名者批准交易 → 签名收集完成后提交 → 节点执行

**关键特征：**
- **分散风险：** 单个签名者私钥泄露不足以为恶
- **不可单点控制：** 任何单独成员都无法支配资金
- **可配合治理：** 结合时间锁、提案流程、阈值调整

**适合：** DAO 金库、大额资金管理、团队协作基金、协议管理密钥

**不适合：** Agent 自动化、高频交易、单人场景

**常见的 M-of-N 配置：**
- 2-of-3：适合初创团队（一个人不在不影响操作）
- 3-of-5：适合 DAO 小委员会
- 4-of-7：适合更分布的管理结构

**必须在人工确认的操作：** 所有交易——因为多签的本质就是多人共识

## AI Agent 视角下的关键洞察

### 为什么 Smart Account 适合 Agent，而 EOA 和多签不适合？

| | EOA | Smart Account | Multisig |
|--|-----|---------------|----------|
| Agent 自动执行 | ❌ 签名即全权，不能委托 | ✅ Session Key + Policy 隔离 | ❌ 每次交易需要多签 |
| 权限粒度 | ❌ 全有或全无 | ✅ 白名单/限额/时间/撤销 | ⚠️ 只有签不签，没有金额限制 |
| 恢复能力 | ❌ 无 | ✅ 可编程恢复 | ⚠️ 签名者变更需要治理 |
| Gas 成本 | ✅ 低 | ❌ 合约调用，稍高 | ❌ 多签提交更贵 |
| Agent 调试 | ❌ 无法区分"是 Agent 还是 Owner 在操作" | ✅ 可通过 Session Key 区分 | ❌ 难以追踪单个 Agent 行为 |

### 风险对照

| 风险类型 | EOA | Smart Account | Multisig |
|----------|-----|---------------|----------|
| 私钥泄露 | ❌ 账户归攻击者 | ✅ Owner 可撤销 + 可分布式恢复 | ⚠️ 需要 M 个私钥（分布风险） |
| 合约漏洞 | ✅ 无合约风险 | ❌ 合约 Bug 可导致资金损失 | ❌ 合约 Bug 可导致资金损失 |
| 人为错误 | ❌ 一次签名=一次损失 | ✅ Policy 可拦截超限操作 | ⚠️ 多人确认降低但非消除风险 |
| 社交攻击 | ✅ 单人不易被社交 | ✅ Policy 不可由 Agent 修改 | ❌ 针对签名者的社交工程 |

---

## 结论

**对 AI Agent 场景的推荐优先级：**

1. **Smart Account** — 最灵活，最适合 Agent 自动执行 + 人工兜底
2. **Multisig** — 适合组织/DAO 的大额资金管理（Agent 可配合提案流程）
3. **EOA** — 仅用于个人小额测试，不适合任何含 Agent 或他人参与的场景

**安全准则：** 无论选用哪种账户类型，Agent 执行路径都需要遵循：
> 白名单合约 → 白名单方法 → 额度策略 → Simulation → Policy 检查 → 用户确认 → 完整 Trace
