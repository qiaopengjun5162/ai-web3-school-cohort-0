## 笔记摘要

### 核心原则：责任分离

Agent 可以替用户发起商业动作，但不能替用户承担无限责任。商业自动化的核心不是让 Agent 随便花钱，而是把购买意图、预算、验收标准和争议规则变成结构化协议。

**购买三阶段：**
- **购买前** → Intent：买什么、为什么买、最多花多少、接受什么结果
- **购买中** → Constraint：报价、有效期、服务条款、数据使用范围、退款条件
- **购买后** → Evidence：任务结果、收据、日志、验收记录、争议路径

---

### Payment Intent

用户授权 Agent 花钱之前的**结构化表达**。本质是把每一次 Agent 购买限制在 bounded risk envelope 内：

```
{
  "intent_id": "...",
  "service_capability": "llm_inference | data_lookup | compute",
  "criteria": { "model": "...", "max_latency_ms": 2000 },
  "budget": { "max_per_call": 0.05, "total_cap": 10.00 },
  "acceptance": { "require_receipt": true, "require_proof": "execution_log" },
  "dispute": { "resolution": "arbitration", "timeout_hours": 24 }
}
```

关键：就算 Agent 模型跑偏或被 prompt injection，**损失上限已知**。

---

### Budget Control

Agentic Commerce 的**安全阀**。Agent 是 constrained spender，不是 unlimited wallet。架构上必须有 **authorization boundary**：
- Agent 可以 negotiate / commit / execute
- 但每笔 expenditure 的 liability cap 由用户在 Payment Intent 中锁定
- Policy 层是唯一跟 AI 模型无关的组件——确定性代码可审计

---

### Proof of Task Completion

不是单一证明，而是一组证据。三种验证路径：

| 路径 | 信任等级 | 成本 |
|------|----------|------|
| 服务方自证（签名日志） | 低 | 低 |
| 第三方见证（TEE 出证） | 高 | 高 |
| 链上验证者网络（预言机） | 中 | 中 |

**最务实路径：** 服务方签名 + 链上哈希验证。服务方跑完任务后签一个 receipt（含 input hash、output hash、timestamp），用户链上验证签名即可。成本低，事后争议有链上锚定。

---

### On-chain Receipt & Escrow

- **链上收据**：不保存完整内容，只保存足够事后核对的证据（input hash、output hash、timestamp）
- **Escrow Flow**：锁定资金 → 服务交付 → 验收 → 释放。超时自动回滚是最后防线
- ERC-8004（Agent 身份/声誉）+ ERC-8183（任务/支付/交付）互补

### Agents Purchasing APIs

Agent 直接购买 API、数据、推理、存储、检索、执行服务的能力。本质是 **agent-oriented marketplace**：
- 服务方注册 capability / pricing / SLA
- Agent 用结构化 query 发现并匹配
- 购买 Intent → Policy Check → Quote Lock → Escrow Hold → 服务交付 → 结算释放

---

### 项目切入方向分析

| 方向 | 切入点 | 难度 | 特点 |
|------|--------|------|------|
| 方向一 | 帮 Agent 购买 API/数据/推理 | ⭐⭐⭐ | 用户获取成本高，平台生意 |
| 方向二 | 帮服务方接受 Agent 支付 | ⭐ | **最快 MVP：Agent Payment Gateway** |
| 方向三 | 帮用户管理预算/权限/审计 | ⭐⭐ | 最强 defensibility，但偏后台 |
| 隐藏方向 | Agent Commerce Discovery Layer | ⭐⭐ | agent-oriented marketplace |

**推荐优先方向二：** 服务方挂一个 endpoint，Agent 带着 signed Payment Intent 来请求服务，网关验证 intent → 扣款（USDC）→ 执行 → 出证，一个 flow 搞定。

---

## 今日收获

Agentic Commerce 把 Agent、钱包、权限、支付、托管、声誉和验证串成一条商业闭环。核心设计原则是 **"替用户发起动作但不替用户承担无限责任"**，所有架构都围绕 bounded risk envelope 展开。Payment Intent 是最关键的原子单元——它把"用户想买"到"Agent 执行"之间的信任缺口用结构化协议填上。
