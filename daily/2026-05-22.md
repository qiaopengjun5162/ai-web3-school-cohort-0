**笔记摘要：**

**Evaluation 要点：**
- Harness：框架负责喂样本→跑系统→收集输出→评分→记录结果
- Golden Set：30~100 条高质量标注样本，覆盖正常/边界/高风险/历史 bug
- LLM-as-Judge：用模型评模型（适合开放式答案），但不能神化，需定期校准
- Regression：修 A 不能坏 B，每次改动重新跑历史样本
- Observability：上线后的真实行为追踪 — 输入、检索、工具调用、错误、成本
- 核心原则：不能被重复测量的 AI 行为，就不能被稳定改进

**Fine-tuning 要点：**
- Fine-tuning 不是第一步 — 应先排除 prompt、context、RAG、schema、eval 的问题
- SFT（监督微调）：用输入-期望输出让模型学某类任务的回答方式，对数据质量极度敏感
- LoRA / PEFT：参数高效微调，降低实验成本但任务定义和数据质量仍决定效果
- Dataset 核心资产：训练集、验证集、测试集、回归集 — 不要把测试集拿去训练
- Overfitting：样本太少、风格单一、轮数太多都会导致真实用户一问就崩
- 不适合替代：链上状态查询、安全审计、交易模拟、权限控制、外部事实引用

**Inference 要点：**
- API Model：上手快，但需处理速率限制、重试、成本控制、版本变更。Agent 场景多轮调用会放大成本和延迟
- Local Model：隐私和可控性优先，但受显存、上下文窗口、并发能力限制，适合分类/抽取/代码补全/轻量 Agent
- Quantization（量化）：FP16→INT8/INT4 取舍体积/速度/质量，需用自己任务的样本测试，不能只靠主观体验
- Serving：把模型变成稳定服务 — 并发、队列、流式、缓存、监控、版本管理
- 核心原则：模型能力只有被稳定、可控、可观测地调用，才算进入产品系统
